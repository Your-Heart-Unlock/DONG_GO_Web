# 네이버 저장 장소 가져오기와 분류 보정

2026-11-14 현재 프로젝트 코드를 기준으로 수정했다. 운영 DB에 가져오기·보정 요청을 실행하거나 배포하지 않았다. 원본 1,000개 JSON은 지정된 로컬 경로에서 읽었으며 저장소에 복제하지 않았다.

푸시 전 원격 `dev`의 `84919d57361815016a23e4b39857ffcf7a8ea404`를 먼저 확인했다. 로컬 기준보다 4개 커밋 앞서 있어 원격의 파일 추가·수정·삭제를 작업 폴더에 반영하고, 겹치는 관리자 API 3개와 장소 유틸리티 1개를 병합했다. 원격의 공통 `requireOwner` 인증과 `computeAverageTier` 유틸리티 사용을 유지한다. 이 환경의 `.git`은 읽기 전용이므로 일반 git pull/commit 대신 GitHub 연결로 최신 파일과 병합 결과를 처리하며, 로컬 Git 기록은 갱신하지 못한다.

## 데이터와 분류

- `originalCategory`: 제공자, 원본 분류명(`mcidName`), 코드(`mcid`), `cidPath`를 보존한다.
- `categoryKey`, `category`: 기존 앱의 최종 카테고리와 표시명이다. `categoryCode`는 원본 코드 호환 필드로 유지한다.
- `classification`: `source`(manual/rule/llm/unresolved), `reason`, `needsReview`, 규칙 `version`을 기록한다.
- 수동 분류와 LLM 적용은 관리자 로그에 이전·이후 분류, 작업자, 시간을 남긴다. 가져오기는 작업자와 결과를 로그에 기록한다.
- 원본 `memo`는 가져오기 후 `importMemo`에 보존한다. 기존 사용자 메모나 연결 문서를 교체하지 않는다.

`DINING`/“음식점”만으로는 요리 종류를 알 수 없다. 상세 경로·원본 분류명·장소명 키워드·근거가 있는 상위 요리 계열을 차례로 확인하고, 모두 적용되지 않으면 `Idle`로 남긴다. 확실한 비음식 장소 분류(공원·박물관 등)와 정육점은 `Other`로 구분한다. 쇼핑은 식품 판매점도 포함하므로 떡집 등 구체적인 음식 키워드를 먼저 확인한다.

### 숫자 경로 근거

`scripts/build-category-evidence.cjs`가 기존 `initial_data`의 폴더 분류와 경로를 대조한다. 숫자 코드의 뜻을 사전처럼 추정하지 않는다.

- 깊이 3 이상인 경로는 서로 다른 장소 ID 2개 이상이 같은 카테고리로 모이거나, 최다 분류가 3표 이상이고 조정 지지율이 80% 이상일 때 사용한다. 소수의 다른 폴더 기록 때문에 전체를 보류하지 않는다. 중식 39개·한식 1개인 경로도 중식으로 처리한다. 원본 폴더 파일은 수정하지 않는다.
- 가장 구체적인 지원 경로를 먼저 확인한다. 지원이 부족한 하위 경로는 지원되는 상위 경로를 확인한다.
- 고기·해산물 표가 3개 이상이면 포괄적인 한식 표는 세부 음식 분류를 반대하는 표로 계산하지 않는다. 다른 요리 계열의 표는 충돌 근거로 유지한다. 원본 표 수와 조정 지지율은 분류 근거에 남긴다.
- 구체적인 경로와 키워드가 모두 없으면 깊이 2의 상위 요리 계열을 마지막으로 사용한다. 이때도 기존 폴더의 요리 계열 표가 5개 이상이고 지지율이 80% 이상이어야 한다. 고기·해산물·스낵·카페·술 폴더는 요리 계열 표에서 제외한다.
- `CAFE`, `BAR`는 네이버의 명시적 원본 대분류로 처리한다.
- `피햄치.json`은 한 카테고리로 취급하지 않는다. 개별 장소명에서 피자·버거·치킨 등의 명확한 키워드가 확인되는 행만 양식/스낵 경로 근거로 사용한다. 치킨은 현재 체계의 Snack, 피자·버거는 West로 처리한다.
- 생성된 `categoryEvidence.json`에는 171개 경로의 원본 표 수·출처 파일·결정 기준·조정 지지율이 들어 있다. 키가 없는 충돌 경로와 상위 계열 기록도 포함한다. `initial_data`는 기존처럼 git에서 제외되며, 생성한 규칙 파일만 저장소에 포함한다.

`categoryKeywords.ts`에 한국어 키워드와 영어 패턴 297개를 정의했다. 경양식돈까스는 West, 해물짬뽕은 China, 갈비탕은 Korea로 처리해 단순 재료 단어보다 구체적인 요리명을 우선한다. 일반 한식 경로에 고기·해산물 단어가 있으면 세부 분류로 보완한다. 원본 CAFE/BAR와 지원되는 구체적인 비한식 경로는 이름의 약한 단어보다 우선한다. 한일식당·천일식당·산중식당·신한양 식당·산야초밥상 등 단어가 겹치는 사례도 검사한다. 주소나 메모의 단어는 분류 키워드로 사용하지 않는다.

규칙 버전은 `local-corpus-keywords-v2`다. 숫자 코드의 공식 명칭을 확인한 사전이 아니며, 자동 분류 범위는 정답 정확도를 뜻하지 않는다. 장소별 근거를 가져오기 미리보기에서 확인하고 수정할 수 있다.

## 가져오기 절차

1. `npm run dev`로 로컬 앱을 실행하고 owner 계정으로 로그인한다.
2. `/admin/import`에서 `naver_saegip_1000.json`을 선택한다. JSON 붙여넣기도 가능하다.
3. **미리보기 생성**을 누른다. 이 요청은 읽기 전용이다. 전체 행의 원본 분류·경로, 최종 분류, 근거, 검토 여부, 중복 후보를 확인할 수 있다.
4. 필요한 행의 카테고리를 직접 선택한다. 해당 행은 `manual`로 기록된다. “분류 검토 대상만 표시”를 사용할 수 있다.
5. 기본 중복 정책 **기존 장소 건너뛰기**를 유지한다. UPDATE도 기존 수동 분류를 보존한다. 카카오/네이버 동일 장소 후보는 UPDATE에서도 제외한다.
6. **저장** 버튼과 확인 창을 통해 적용한다. `Idle`도 저장 가능하며 이후 카테고리 관리 화면에서 검토한다.

직접 JSON API를 사용할 때도 서버에서 ID, 유한 좌표와 범위, 필수 문자열, 원본 경로, 카테고리, 중복 정책을 검사한다. 서버가 규칙 분류를 다시 계산하므로 클라이언트의 규칙 결과를 무조건 신뢰하지 않는다. 신규 등록자는 요청 본문 대신 인증 토큰에서 정한다. 한 번에 최대 2,000행, 파일 선택은 20MB 이하이다.

### 기존 장소와 연결 보존

네이버 ID 또는 `naverPlaceId` 별칭으로 일치하면 기존 문서 ID를 사용한다. 기존 문서는 필요한 필드만 갱신한다. `createdBy`, `createdAt`, 리뷰, 평점, 사진 및 다른 컬렉션의 연결을 교체하지 않는다.

이름을 공백·문장부호 제거 후 비교하고, 주소 일치 또는 약 30m 이내 좌표가 함께 확인되면 동일 장소 후보로 보류한다. 제공자가 다른데 숫자 ID만 충돌해도 보류한다. 후보를 자동 병합하지 않는다. API도 미리보기와 같은 판단을 반복한다. 파일 내 동일 ID 중복은 오류로 거부한다.

출처가 없는 기존 명시적 카테고리는 보수적으로 보호한다. 과거 `Other`이며 원본 코드가 DINING/CAFE/BAR이거나 원본 표시명이 “음식점”인 행은 검토 대상이다. 원본 코드가 없고 `Other`만 남은 경우 수동 선택일 가능성이 있어 자동 변경하지 않는다.

## 기존 데이터 보정과 LLM

`/admin/categories`의 **기존 데이터 규칙 보정 미리보기**는 저장하지 않고 후보의 이전·제안 분류와 근거를 보여준다. 불필요한 행을 체크 해제한 뒤 **검토한 결과 저장**을 눌러 적용한다. 충분한 근거가 없는 기존 Other 음식점은 Idle로 보정할 수 있다. 원본 코드 삭제 기능은 비활성화했다.

미분류 목록과 총개수는 동일한 `needsCategoryReview()` 함수를 사용한다. 누락된 categoryKey, Idle, 검토 플래그, 과거 Other 음식점을 함께 다룬다. 확인된 Other는 미분류에 포함하지 않는다. manual Idle은 목록에서 확인할 수 있지만 자동 보정과 LLM 대상에서는 보호한다.

LLM 보조 절차:

1. 장소 목록을 불러온다. 50개씩 추가로 불러올 수 있다.
2. 규칙 보정을 먼저 적용한 뒤 **규칙 미분류만 LLM 프롬프트 복사**를 누른다. 현재 규칙으로도 분류할 수 없는 행만 포함된다. 장소 ID·이름·주소·원본 분류·cidPath와 Idle 허용 지시가 포함된다. 수동 분류와 규칙으로 처리할 수 있는 행은 제외한다.
3. 사용자가 선택한 LLM에 직접 붙여넣는다. 복사 자체로 장소 데이터를 외부에 전송하지 않는다.
4. `[{"placeId":"...","categoryKey":"Idle","reason":"정보 부족"}]` 형태의 응답을 붙여넣는다.
5. **LLM 결과 미리보기**에서 ID·허용 카테고리·근거·중복 응답을 검증한다. 불필요한 행을 제외하거나 카테고리를 바꿀 수 있다. 바꾼 행은 manual로 기록한다.
6. 결과를 검토한 뒤 저장한다. 서버도 실제 문서 존재 여부, 이전 카테고리, 수동 분류 보호, 현재 규칙으로도 미분류인지 다시 검사한다. 동시 변경이 있으면 충돌로 중단한다. 저장은 200개 단위이며 일부 묶음이 실패하면 이미 저장한 수를 알린다.

자동 LLM API 연동은 추가하지 않았다. API 키나 유료 API 실행이 필요 없다. LLM이 지어낸 근거까지 코드로 사실 검증할 수는 없으므로 적용 전 검토가 필요하다.

일반 장소 추가·재활성화와 사용자 수정 요청 승인 경로에서도 수동 출처를 기록하도록 보완했다.

## 남은 한계

- 기존 분류 폴더는 정답표가 아니다. 다수결·키워드·상위 계열로 자동 범위를 넓힌 만큼 오분류 가능성이 있다. 특히 복합 메뉴나 특이한 상호는 미리보기에서 검토하고, 정확도를 높이려면 공식 분류표나 직접 검토한 경로별 분류가 필요하다.
- 예전 코드가 이미 삭제한 원본 분류는 복원할 수 없다. 원본 JSON으로 동일 네이버 ID를 UPDATE하면 원본 정보를 보충할 수 있다.
- 운영 DB 연결을 실행하지 않았으므로 기존 운영 데이터와의 실제 중복 개수는 아직 집계하지 않았다. 로그인 후 미리보기를 통해 확인한다.
- 제공자 간 이름·주소 표기 차이, 지점명 차이로 중복 후보를 놓칠 수 있다. 이미 연결된 별칭은 정확히 대조하지만 후보 자동 병합·수동 연결 UI는 추가하지 않았다.
- 미분류 집계와 레거시 중복 확인을 위해 전체 장소를 읽는다. 대규모 데이터에서는 읽기 비용과 응답 크기를 줄이도록 검토 플래그·정규화 키의 별도 인덱스/이관이 필요하다.
- 서로 다른 ID의 동일 장소를 여러 사용자가 동시에 신규 등록하는 경쟁은 전역 잠금으로 막지 않는다. 같은 문서 ID에 대한 덮어쓰기와 카테고리 변경 충돌은 트랜잭션으로 보호한다.
- 실제 브라우저의 로그인·운영 Firestore 통합 테스트는 수행하지 않았다. 검증 범위는 실제 파일 기반 분류, 메모리 DB를 사용한 API 테스트, 타입 검사와 빌드이다.
